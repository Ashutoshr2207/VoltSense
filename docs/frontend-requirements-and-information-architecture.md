# VoltSense: Frontend Requirements & Information Architecture

**Review date:** 2026-10-20 · **Source snapshot:** `d65bf84`, branch inspected with a clean working tree. **Scope:** source/document/data inspection only; no tests, live-service verification, configuration changes or UI implementation. This document defines information requirements, not a visual redesign or authorization to change contracts.

**Status key:** **Supported** = an implemented data/API path exists, not a claim of scientific validation or a newly verified runtime result. **Partial** = data or logic exists but its presentation, provenance, persistence or semantics are incomplete. **Not supported** = no defensible current source/contract for the claim.

## 1. User goals and the actual journey

Users need to: identify which vehicle and source cell a report describes; upload suitable data; understand what was accepted, skipped or rejected; distinguish observed capacity from experimental model estimates; inspect trends and screening findings; revisit the exact dataset/report; and understand the next useful action without mistaking a research estimate for a safety decision.

Current flow: register/sign in → create the account's **single vehicle profile** → SOH & RUL upload → Express parses/stores CSV/XLS/XLSX and diagnostics → explicit processing returns a run ID → frontend polls saved status → eligible cycle histories reach Python → completed results/insights/notifications are persisted → vehicle summary and Insight history retrieve completed reports. Failures retain dataset/run information and compensate incomplete result writes. A diagnostics-only completed report may have null SOH/RUL; “processed” does not mean every analysis was eligible.

**Important current contradiction:** [model_loader.py](../ml-service/model_loader.py) now defaults to V3 and permits an unapproved bundle as experimental; [app.py](../ml-service/app.py) returns it through ordinary `/predict`. [analysisPipelineService.js](../backend/src/services/analysisPipelineService.js) saves it in ordinary predictions and updates vehicle summaries. The former separate preview route is absent from current [dataset routes](../backend/src/routes/datasetRoutes.js). This conflicts with approval/isolation guardrails in [AGENTS.md](../AGENTS.md), and with older disabled-inference descriptions in [rebuild-contract.md](rebuild-contract.md) and [sample README](../sample-data/README.md). Requirements must reflect this present behavior while identifying the unresolved policy gap; the UI must not describe these persisted results as approved or isolated temporary previews.

## 2. Page requirements and intended interactions

Retain existing destinations: Dashboard, Battery Anomalies, SOH & RUL, Charging, Insight, Vehicle Profile, Settings, Help. Upload is part of SOH & RUL; history and report detail are inside Insight, not additional standalone pages. Header context should identify the active vehicle, selected source battery where available, report/dataset and account; notifications link to the relevant report, not an unrelated latest result.

## 3. Metric and evidence rules

| Information | Required meaning/presentation | Actual source / limit |
|---|---|---|
| **Observed SOH (%)** | Capped `100 × latest observed discharge Ah / first observed discharge Ah`; identify both cycles. This is capacity-derived arithmetic, not an independently measured BMS SOH or proof the reference was brand new | `Dataset.soh.empirical`, `Prediction.prediction.measuredSoh`, raw `cycleTable`; parser reference is first discharge |
| **Model SOH (%)** | Separate experimental estimate, with candidate version and same reference. Differences from observed SOH use **percentage points**, not an “accuracy %” | `prediction.modelSoh`/`soh`; capacity-model output converted once using Q1; 13 features use capacity history before target cycle |
| **Capacity (Ah)** | Distinct observed latest capacity, model-predicted capacity, first-reference capacity; signed change in Ah and relative %. Never label a model value “measured”; show recovery/variation rather than absolute-loss-only wording | `dataset.soh.currentCapacityAh` or latest valid raw cycle versus `Prediction.prediction.currentCapacityAh`, which currently receives **model output** when inference succeeds |
| **RUL (cycles)** | Completed discharge cycles remaining to the first observed 80% SOH crossing. Identify target/current cycle. Zero after an observed crossing is a terminal-history rule, not a forecast; no automatic conversion to years, distance or calendar EOL | `rulCycles`, `estimatedEOLCycle`, raw capacity history and Python terminal policy. Censored training histories have unknown labels; a displayed candidate forecast is not ground truth |
| **Historical degradation** | Capacity Ah and empirical SOH % against original cycle ordinals; visible gaps and source context. A single model estimate is a marker, not an invented future trajectory. Do not join different cells/protocols/references into one line | Raw cycle table plus `degradation.historical`; persisted curve is sampled to roughly 48 intervals. `degradation.predicted` is empty. Future forecast curve not supported |
| **Voltage/current/temperature** | V/A/°C with cell-versus-pack and mean/min/max scope, phase, sample count and date range. Missing signals remain unknown. Cycle-summary extrema are not sensor-trace extrema | Parser `columnStats`, `cycleTable`, optional spreads. Cycle aggregation can combine charge/discharge source rows; summary provenance must be explicit |
| **Phase share / sessions** | Use `timeShare.method`: observation-count proportion is not “time spent.” Even elapsed-time estimates from sparse summaries require a warning. Energy uses kWh with integration/summary-estimate basis and coverage | `timeShare`, `chargingSessions[].energyBasis/status/warnings`. No automatic Ah↔pack-kWh interpretation or guaranteed full-session reconstruction |
| **Anomalies** | “Reference-limit excursions,” not confirmed faults. Show coverage before counts; null/zero analyzed rows means not evaluated, not safe. No critical-current claim where current limits are null | Generic profile: cell 2.8–4.25 V, spread 0.15 V, documented temperature/SoC screens. No manufacturer verification, pack-voltage/current fault limits, or resolution endpoint |
| **Model evaluation** | Optional expandable offline context: MAE/RMSE with units, R² separately, population and baseline; never a live confidence/accuracy percentage | V3 capacity RMSE 0.02078 Ah versus persistence 0.02066 Ah; RUL evidence is one previously inspected test battery. Confidence is uncalibrated/null; no confidence interval or EV-pack validation |

Every numeric display requires a source category, scope and freshness. SOH “healthy/attention/critical” bands are heuristic capacity classifications, separate from anomaly severity and model readiness; none certifies vehicle safety. SOH is not SoC. A synthetic input remains synthetic even when its prediction comes from a genuine model.

## 4. Upload and outcome requirements

- **Before upload:** owned vehicle, filename/format/size, clearly preliminary header/sample preview, required units and supported aliases. Web uploads are CSV/XLS/XLSX; raw NASA MAT/ZIP and the unified research catalogue are not automatically supported upload formats. Excel uses its first worksheet. Show the configured size limit, not an invented fixed allowance.
- **For SOH/RUL:** one identified source cell, explicit original discharge cycles 1..t, at least seven positive finite complete-discharge capacities in Ah; disclose missing/colliding columns, units, conflicting capacities, duplicates and gaps. Physical completeness/reference credibility cannot be established merely by a syntactically valid CSV. Show available/selected battery IDs and limitations of switching; do not imply verified manufacturer mapping.
- **During processing:** bind to returned `pipelineRunId`; show real queued/processing/completed/failed states. Preserve seven existing stage names. The first five Node stages can finish together; Python feature/preprocessing stages complete only with successful inference. No fabricated percentage or elapsed-time success.
- **After processing:** per-analysis outcomes for validation, anomalies, charging extraction, SOH and RUL, with reason and useful next action. “Completed with skipped analyses” differs from total failure. Communication failure, malformed response, invalid input and missing/incompatible model require different explanations. Preserve prior report context while clearly saying the latest attempt failed; never relabel the prior result as the new upload.
- **Next actions:** correct/re-upload bad data, explicitly retry a stopped run/service, inspect diagnostics, open the exact saved report or return later to saved status. Refresh is read-only. Identical-byte upload reuses a dataset; explicit processing creates another attempt. Current UI has no dataset-delete control; the owned delete API exists. Do not promise all-attempt history or deletion UI as already implemented.

## 5. History, dates and successive snapshots

Keep four concepts distinct: **source observation time** (`cycleTable.date`/source timestamp), **snapshot measurement date** (`measurementDate`), **file upload time** (`Dataset.uploadedAt`) and **analysis creation/completion time** (`Prediction.createdAt`, run timestamps). Preserve timezone/precision; date-only or undated input must not acquire an invented measurement time. Display the raw source date alongside an explicitly labelled display timezone where needed. Relative “last analyzed” time is secondary to an absolute date.

A historical report links vehicle → dataset → source cell → run → prediction → insight. Sort measurement snapshots by measurement date for degradation review; sort operational events by their actual operation timestamps. Reprocessing the same cycle is a new analysis attempt, not a new battery event. Do not collapse distinct reports solely by final cycle number. Compare snapshots only when cell identity, first reference, units and protocol are compatible; current IDs do not prove physical battery lineage across uploads.

Inspected demonstration inputs:

| CSV | Source rows / discharge cycles | Source chronology | Required interpretation |
|---|---:|---|---|
| `demo_battery_cycles.csv` | 40 / 40 | No measurement dates | Synthetic discharge summaries; no charging sessions/SoC, no authentic elapsed-time evidence |
| `demo1_battery_cycles.csv` | 80 / 40 | 2024-12-07 through 2025-01-15 | Charge/discharge summary pair per cycle |
| `demo2_battery_cycles.csv` | 160 / 80 | Same start, through 2025-06-14 | Cumulative extension, not 80 additional cycles |
| `demo3_battery_cycles.csv` | 240 / 120 | Same start, through 2025-11-11 | Cumulative extension |
| `demo4_battery_cycles.csv` | 320 / 160 | Same start, through 2026-04-10 | Cumulative extension; last observed capacity 1.5992 Ah is below 80% of the 2-Ah reference |

All use `SYNTHETIC_DEMO_CELL_001`. The four dated files contain nested histories of **one synthetic cell**, not four independent batteries. Do not sum their cycle counts, energy or repeated anomalies as new activity. They demonstrate history navigation, not model accuracy or real degradation. Their shared 13 CSV columns are a file schema, distinct from the model's 13 engineered features.

**Unit limitation:** the original CSV contains `discharge_duration=4527` at cycle 40 (seconds); the dated files contain `75.5` for that same cycle. Their generator computes minutes, while the parser copies this field directly into the duration value exposed as seconds. Charging summaries use another minutes-based branch. Duration/energy/phase comparisons must remain qualified until this source-to-unit contract is resolved; do not present those demo outputs as verified charging behavior. Inspection read these files without executing the generator.

## 6. Information hierarchy and consolidation

1. **Always visible first:** active vehicle/source cell, selected dataset/report, measurement freshness, experimental/synthetic/unavailable labels and any failed run or significant screening finding. Then the user's next action.
2. **Primary evidence:** separately labelled observed and model SOH/capacity, RUL meaning/threshold, and one relevant observed history chart/table tied to that same source. Each result carries **EXPERIMENTAL — NOT VALIDATED FOR REAL-WORLD DECISIONS** when applicable, including dashboard/history/detail/AI contexts.
3. **Secondary/expandable:** raw cycle rows, quality counts, stage timestamps, model hash/version/evaluation context, threshold specifications, calculation basis and explanation provenance. Nulls explain why data is absent; loading/failure/empty/skipped remain separate states.
4. **Consolidate:** one authoritative upload/status summary; one report-detail destination; one explanation entry point under Insight. SOH's mini anomaly list and Dashboard's finding should link to full Battery Anomalies rather than repeat the same table. Its cycle evidence and Insight history have different purposes; label them accordingly.
5. **Demote or omit from diagnostic claims:** illustrative 3D pack/modules, repeated generic recommendations, unsupported chemical loss breakdowns, fake live controls and redundant healthy badges. The 16-module model is an illustration colored by one overall value, not module-level observations. Presence of a chart/component does not establish data availability.

Resistance/imbalance may exist only with suitable signal evidence; absent inputs must not become diagnostic values. The main “pack voltage” display also lacks a consistent binding to the parser's available voltage statistics.
